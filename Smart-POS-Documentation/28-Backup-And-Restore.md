# 28 — Backup & Restore (النسخ الاحتياطي والاستعادة)

> بيانات **Smart ERP POS** مالية ومحاسبية لآلاف المستأجرين. فقدان بيانات = فقدان أموال وثقة. هذا الملف يحكم استراتيجية النسخ والاستعادة على **SQL Server 2022** بما يحقّق **RPO/RTO** صارمين، مع مراعاة نموذج تعدّد المستأجرين.

---

## 1) الأهداف (RPO / RTO)

| المؤشّر | التعريف | الهدف |
|---------|---------|-------|
| **RPO** (Recovery Point Objective) | أقصى فقد بيانات مقبول | **≤ 5 دقائق** (بفضل Log Backups المتكرّرة) |
| **RTO** (Recovery Time Objective) | أقصى زمن للعودة للتشغيل | **≤ 30 دقيقة** لقاعدة كاملة |
| **Point-in-Time** | الاستعادة للحظة محدّدة قبل حادث | مدعومة ضمن نافذة الاحتفاظ |

> تحقيق `RPO ≤ 5 دقائق` يتطلّب نموذج استرداد **FULL Recovery Model** مع نسخ سجلّ المعاملات (Log Backups) كل 5 دقائق.

---

## 2) نموذج الاسترداد (Recovery Model)

قاعدة الإنتاج تعمل بنموذج **FULL**:

```sql
ALTER DATABASE [SmartPos] SET RECOVERY FULL;
```

| النموذج | متى | نتيجة |
|---------|-----|-------|
| **FULL** | الإنتاج | يدعم Point-in-Time وLog Backups؛ RPO دقائق |
| **SIMPLE** | Dev فقط | لا Log Backups؛ لا Point-in-Time |
| **BULK_LOGGED** | نوافذ استيراد ضخم مؤقّتة | يقلّل حجم الـ log لعمليات bulk، ثم يعود FULL |

---

## 3) استراتيجية النسخ (Backup Strategy)

ثلاثية متكاملة: **Full + Differential + Log**.

| النوع | التكرار | المحتوى | الغرض |
|-------|---------|---------|-------|
| **Full Backup** | يومياً (02:00 UTC) | القاعدة كاملة | خطّ الأساس للاستعادة |
| **Differential** | كل 6 ساعات | التغييرات منذ آخر Full | تقليل زمن الاستعادة |
| **Transaction Log** | كل **5 دقائق** | سجلّ المعاملات | تحقيق RPO منخفض + Point-in-Time |

**نموذج أوامر:**

```sql
-- Full (يومي)
BACKUP DATABASE [SmartPos]
TO DISK = N'/backup/full/SmartPos_FULL_20260713.bak'
WITH COMPRESSION, CHECKSUM, ENCRYPTION
     (ALGORITHM = AES_256, SERVER CERTIFICATE = [BackupCert]),
     STATS = 5;

-- Differential (كل 6 ساعات)
BACKUP DATABASE [SmartPos]
TO DISK = N'/backup/diff/SmartPos_DIFF_20260713_1400.bak'
WITH DIFFERENTIAL, COMPRESSION, CHECKSUM, ENCRYPTION
     (ALGORITHM = AES_256, SERVER CERTIFICATE = [BackupCert]);

-- Transaction Log (كل 5 دقائق)
BACKUP LOG [SmartPos]
TO DISK = N'/backup/log/SmartPos_LOG_20260713_140500.trn'
WITH COMPRESSION, CHECKSUM, ENCRYPTION
     (ALGORITHM = AES_256, SERVER CERTIFICATE = [BackupCert]);
```

**مبادئ إلزامية:**

- **`CHECKSUM`** على كل نسخة للكشف عن تلف الصفحات.
- **`ENCRYPTION` (AES_256)** إجبارية — النسخ تحوي بيانات مالية حسّاسة (يتّسق مع [27-Security.md](27-Security.md)).
- **`COMPRESSION`** لتقليل الحجم وزمن النقل خارج الموقع.
- شهادة النسخ الاحتياطي (`BackupCert`) تُنسَخ وتُحفَظ منفصلة — بدونها لا تُستعاد النسخ المشفّرة.

---

## 4) الجدولة (Scheduling)

عبر **SQL Server Agent Jobs** (أو **Ola Hallengren Maintenance Solution** كمعيار صناعي موصى به):

| المهمّة | Cron/الجدول | ملاحظة |
|---------|-------------|--------|
| Full | يومياً 02:00 UTC | خارج ساعات الذروة |
| Differential | 08:00 / 14:00 / 20:00 UTC | |
| Log | كل 5 دقائق | 24/7 |
| DBCC CHECKDB (سلامة) | أسبوعياً | كشف التلف مبكّراً |
| اختبار الاستعادة | أسبوعياً (§9) | آلي على خادم عزل |

**مبدأ**: يُفضّل **Ola Hallengren's Maintenance Solution** لإدارة النسخ + التحقّق + التنظيف بمعايير مثبتة، بدل سكربتات مخصّصة هشّة.

---

## 5) الاحتفاظ (Retention)

| النوع | مدّة الاحتفاظ | التخزين |
|-------|---------------|---------|
| Log | 7 أيام | تخزين سريع محلّي + نسخة خارج الموقع |
| Differential | 14 يوماً | محلّي + خارج الموقع |
| Full | 35 يوماً محلّي | + أرشيف خارج الموقع |
| Full شهري (أرشيف) | 12 شهراً | تخزين بارد (Cold) خارج الموقع |
| Full سنوي (امتثال) | 7 سنوات | أرشيف طويل الأمد (متطلّبات محاسبية/ضريبية) |

- التنظيف الآلي يحذف ما تجاوز مدّته (مع تسجيل الحذف).
- سياسة الاحتفاظ الطويل (7 سنوات) تُبرَّر بمتطلّبات حفظ السجلّات المالية.

---

## 6) الاستعادة لنقطة زمنية (Point-in-Time Restore)

سيناريو: حادث (حذف خاطئ، تلف) الساعة 14:07، والمطلوب العودة للساعة 14:05 بالضبط.

```sql
-- 1) استعادة آخر Full قبل النقطة — بلا استرداد
RESTORE DATABASE [SmartPos]
FROM DISK = N'/backup/full/SmartPos_FULL_20260713.bak'
WITH NORECOVERY, REPLACE;

-- 2) آخر Differential قبل النقطة
RESTORE DATABASE [SmartPos]
FROM DISK = N'/backup/diff/SmartPos_DIFF_20260713_1400.bak'
WITH NORECOVERY;

-- 3) سلسلة الـ Log حتى اللحظة المطلوبة تماماً
RESTORE LOG [SmartPos]
FROM DISK = N'/backup/log/SmartPos_LOG_20260713_140500.trn'
WITH STOPAT = '2026-07-13T14:05:00', RECOVERY;
```

**التسلسل:** `Full (NORECOVERY)` → `Differential (NORECOVERY)` → سلسلة `Log (NORECOVERY)` حتى ما قبل النقطة → آخر `Log` بـ `STOPAT ... RECOVERY`. `STOPAT` يوقف الاسترداد عند اللحظة المحدّدة بدقّة.

## 7) النسخ على مستوى المستأجر (Per-Tenant) مقابل النسخة الكاملة

نموذجنا **Single Database / Shared Schema**، لذا:

| السيناريو | الحلّ |
|-----------|-------|
| كارثة القاعدة كاملة | استعادة القاعدة كاملة (Point-in-Time) — يخدم كل المستأجرين |
| استعادة/تصدير مستأجر واحد فقط | **Tenant-Scoped Restore** منطقي عبر أداة تصدير/استيراد مفلترة بـ `TenantId` |

**آلية استعادة مستأجر واحد دون المساس بالبقيّة** (سيناريو "العميل حذف بياناته بالخطأ"):

1. استعادة نسخة القاعدة إلى قاعدة **جانبية معزولة** (`SmartPos_Restore`) لنقطة زمنية.
2. استخراج صفوف المستأجر المعنيّ فقط: `WHERE TenantId = @tid` عبر سكربت/أداة (BCP، Export).
3. دمجها بعناية في قاعدة الإنتاج ضمن معاملة مُدقَّقة، مع احترام Soft Delete والعلاقات.

> **ميزة بنيوية**: بفضل `TenantId` في كل جدول أعمال، يمكن دائماً عزل بيانات مستأجر للتصدير أو الاستعادة الانتقائية. عند نموّ مستأجر ضخم مستقبلاً يُنقَل لقاعدة/شارد خاصّ (انظر [24-MultiTenant.md](24-MultiTenant.md)) فيُصبح له نسخه المستقلّ.

**تصدير المستأجر (Data Portability):** مطلوب أيضاً لأسباب تعاقدية (يحقّ للعميل أخذ بياناته). تُصدَّر بيانات المستأجر بصيغة قياسية (JSON/CSV مفلترة بـ `TenantId`).

## 8) التخزين خارج الموقع (Off-Site / 3-2-1)

نلتزم قاعدة **3-2-1**:

- **3** نسخ من البيانات (الإنتاج + نسختان احتياطيتان).
- **2** وسيطين مختلفين (قرص محلّي سريع + تخزين سحابي).
- **1** نسخة **خارج الموقع** (منطقة/مركز بيانات مختلف) — للحماية من كوارث الموقع.

| الطبقة | الموقع | الغرض |
|--------|--------|-------|
| Hot | قرص محلّي على خادم DB | استعادة سريعة |
| Warm | تخزين سحابي (Blob/S3) نفس المنطقة | حماية من فشل الخادم |
| Cold/Off-site | منطقة جغرافية مختلفة، Immutable/WORM | حماية من الكوارث و**Ransomware** |

- النسخ خارج الموقع **مشفّرة** ويفضّل أن تكون **Immutable (WORM)** لمنع حذفها من قبل مهاجم (حماية من الفدية).
- نقل النسخ يتمّ عبر قناة مشفّرة، والوصول للتخزين البارد بصلاحيات دنيا منفصلة.

---

## 9) اختبار الاستعادة (Restore Testing)

> **قاعدة ذهبية:** نسخة احتياطية لم تُختبَر استعادتها = لا نسخة احتياطية.

- **آلياً أسبوعياً**: يستعيد الخطّ آخر Full + Diff + Log على **خادم عزل**، ثم:
  - يشغّل `DBCC CHECKDB` للتحقّق من السلامة.
  - يشغّل استعلامات تحقّق (عدد الفواتير، مجاميع مالية) مقابل قيم متوقّعة.
  - يقيس **زمن الاستعادة الفعلي** ويقارنه بـ RTO.
- **تمرين استرداد كوارث (DR Drill)** ربع سنوي: محاكاة فقد كامل والعودة للتشغيل، مع توثيق الزمن والعقبات.
- نتائج كل اختبار تُسجَّل؛ فشل الاستعادة = حادث أمني/تشغيلي يُصعَّد فوراً.

---

## 10) إشعار فشل النسخ (Backup Failure Alerting)

- كل مهمّة نسخ تُبلّغ حالتها (نجاح/فشل) إلى نظام المراقبة (APM/Serilog → Seq) — انظر [29-Performance.md](29-Performance.md).
- **فشل نسخة**، أو **فوات نافذة زمنية** (لم تُنفَّذ نسخة log خلال 10 دقائق)، يُطلق **تنبيهاً فورياً** (Email/Slack/PagerDuty) للفريق.
- مراقبة **سلسلة النسخ (Backup Chain)**: انقطاع السلسلة (log مفقود) يمنع Point-in-Time ⇒ تنبيه حرج.
- لوحة مراقبة تعرض: آخر Full/Diff/Log ناجح، حجمها، ونتيجة آخر اختبار استعادة.

---

## 11) قائمة تدقيق النسخ والاستعادة (Checklist)

- [ ] قاعدة الإنتاج بنموذج **FULL Recovery**.
- [ ] Full يومي + Differential كل 6 ساعات + Log كل 5 دقائق.
- [ ] كل النسخ بـ `CHECKSUM` + `COMPRESSION` + تشفير `AES_256`.
- [ ] شهادة النسخ محفوظة منفصلة وآمنة.
- [ ] سياسة احتفاظ متدرّجة تشمل أرشيف امتثال 7 سنوات.
- [ ] قاعدة 3-2-1 مع نسخة خارج الموقع Immutable.
- [ ] Point-in-Time مُختبَر ويحقّق RPO ≤ 5 دقائق و RTO ≤ 30 دقيقة.
- [ ] آلية استعادة/تصدير مستأجر واحد جاهزة ومُختبَرة.
- [ ] اختبار استعادة آلي أسبوعي + DR Drill ربع سنوي.
- [ ] تنبيه فوري عند فشل نسخة أو انقطاع سلسلة الـ log.
