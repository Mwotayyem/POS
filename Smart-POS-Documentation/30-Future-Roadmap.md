# 30 — Future Roadmap (خارطة الطريق المستقبلية)

> خارطة طريق مرحلية لتطوّر **Smart ERP POS** من **MVP** إلى منصّة SaaS ناضجة قابلة للتوسّع لعشرات الآلاف من المستأجرين. الترتيب يعكس الأولوية بحسب **القيمة للعميل × الجدوى التقنية**. تتّسق هذه الخارطة مع النطاق في [01-Project-Overview.md](01-Project-Overview.md) واستراتيجية التوسّع في [03-Database-Strategy.md](03-Database-Strategy.md).

---

## 1) المبادئ الحاكمة للأولويات (Prioritization Principles)

1. **الأساس قبل التوسّع**: لا نبني caching أو sharding قبل استقرار النواة المحاسبية وعزل المستأجرين.
2. **القيمة المباشرة للعميل أولاً**: ميزة يستخدمها الكاشير يومياً تسبق ميزة بنية تحتية غير مرئية.
3. **لا نكسر النواة**: كل مرحلة تُبنى فوق [02-System-Architecture.md](02-System-Architecture.md) دون إعادة كتابة الطبقات.
4. **قابلية القياس مصمّمة مسبقاً**: `TenantId` كمفتاح تقسيم موجود من اليوم الأول (انظر [03](03-Database-Strategy.md) §5)، فالتوسّع تفعيل لا هجرة مؤلمة.

---

## 2) نظرة عامة على المراحل (Phases at a Glance)

```
Phase 1: MVP           ──▶  نظام بيع وشراء ومخزون يعمل لمستأجر واحد فعلياً
Phase 2: Multi-Tenant  ──▶  عزل، تخصيص، صلاحيات، لوحة تحكّم لحظية
Phase 3: Scale & Mobile──▶  Redis، تطبيق جوّال، تقارير متقدّمة، Read Replicas
Phase 4: Intelligence  ──▶  AI forecasting، WhatsApp، e-Invoicing، تكاملات
Phase 5: Platform      ──▶  Sharding، Marketplace، domain-per-tenant، API عام
```

| المرحلة | الهدف الرئيسي | الحالة |
|---------|----------------|--------|
| **Phase 1 — MVP** | نواة تشغيلية تعمل | 🟡 قيد البناء |
| **Phase 2 — Multi-Tenant SaaS** | جاهزية البيع التجاري | ⬜ مخطّط |
| **Phase 3 — Scale & Mobile** | أداء وانتشار | ⬜ مخطّط |
| **Phase 4 — Intelligence & Integrations** | تمييز تنافسي | ⬜ مخطّط |
| **Phase 5 — Platform & Ecosystem** | منصّة قابلة للتوسّع | ⬜ رؤية |

## 3) Phase 1 — MVP (النواة التشغيلية)

**الهدف:** نظام قابل للاستخدام الفعلي — بيع، شراء، مخزون، تقارير أساسية — بمعمارية نظيفة وقاعدة بيانات مطبّعة.

| الميزة | الوصف | الأولوية |
|--------|-------|----------|
| Catalog | منتجات، باركود، وحدات، تصنيفات | 🔴 حرجة |
| Purchasing | فواتير شراء + استلام + تحديث مخزون | 🔴 حرجة |
| Inventory | أرصدة + حركات (StockMovements) | 🔴 حرجة |
| Sales + POS | فواتير بيع، شفت كاشير، صندوق نقدية | 🔴 حرجة |
| Partners | موردون + عملاء أساسيون | 🟠 مهمّة |
| Auth أساسي | تسجيل دخول + JWT | 🔴 حرجة |
| تقارير أساسية | مبيعات/مخزون بسيطة | 🟠 مهمّة |

**معايير الخروج (Exit Criteria):**
- عملية بيع كاملة ذرّية (فاتورة + بنود + خصم مخزون + حركة صندوق).
- كل جدول ملتزم بمعايير [04-Database-Design.md](04-Database-Design.md) (أعمدة مشتركة، Soft Delete، `DECIMAL(18,4)`).
- Clean Architecture مطبّقة عبر الطبقات الخمس.

---

## 4) Phase 2 — Multi-Tenant SaaS (الجاهزية التجارية)

**الهدف:** تحويل النواة إلى منتج SaaS قابل للبيع لعملاء متعدّدين من نشر واحد.

| الميزة | الوصف | الأولوية |
|--------|-------|----------|
| عزل المستأجرين | Global Query Filter + `ITenantProvider` من JWT | 🔴 حرجة |
| RLS (defense-in-depth) | Row-Level Security على مستوى المحرّك | 🟠 مهمّة |
| RBAC كامل | أدوار وصلاحيات دقيقة + Claims | 🔴 حرجة |
| Refresh Token + OTP | جلسات آمنة، استرجاع دخول | 🟠 مهمّة |
| التخصيص (White-label) | شعار، ألوان، عملة، ضريبة، لغة، RTL — عبر الإعدادات | 🔴 حرجة |
| فروع/متاجر متعدّدة | `StoreId`، تحويلات بين الفروع | 🟠 مهمّة |
| مرتجعات (بيع/شراء) | إغلاق دورة المستندات | 🟠 مهمّة |
| عروض وترويج | Offers, OfferRules, تتبّع استخدام | 🟡 لطيفة |
| SignalR | إشعارات ولوحة تحكّم لحظية | 🟠 مهمّة |
| Audit Log كامل | تدقيق كل تغيير مع `TenantId`/`UserId` | 🔴 حرجة |
| Onboarding ذاتي | تفعيل مستأجر جديد < 10 دقائق (هدف [01](01-Project-Overview.md)) | 🟠 مهمّة |

**معايير الخروج:** اختبارات عزل آلية تثبت صفر تسرّب بين المستأجرين؛ تفعيل مستأجر جديد دون تدخّل هندسي.

---

## 5) Phase 3 — Scale & Mobile (الأداء والانتشار)

**الهدف:** تحمّل النمو، تسريع القراءة، والوصول للأجهزة المحمولة.

| الميزة | الوصف | الأولوية |
|--------|-------|----------|
| **Redis Cache** | تخزين مؤقّت للـ Catalog، الإعدادات، الجلسات، بيانات المرجع | 🔴 حرجة |
| **Read Replicas** | فصل قراءة التقارير عن كتابة POS (مع RCSI) | 🟠 مهمّة |
| **تطبيق جوّال (Mobile App)** | كاشير/مخزون على الجوّال (يستهلك الـ API — [25](25-API-Design.md)) | 🟠 مهمّة |
| **POS يتحمّل الانقطاع (Offline-tolerant)** | طابور محلي + مزامنة عند العودة | 🟡 لطيفة |
| تقارير متقدّمة | لوحات تفاعلية، تصدير، جدولة عبر Hangfire | 🟠 مهمّة |
| Materialized Summaries | جداول ملخّص يومي مُجمّعة مسبقاً (de-norm مبرَّر — [03](03-Database-Strategy.md) §6) | 🟡 لطيفة |
| تحسين الفهرسة والاستعلامات | Covering indexes، مراجعة خطط التنفيذ | 🟠 مهمّة |

**ملاحظة على Redis:** يُدخَل عند وجود حمل قراءة حقيقي، لا استباقياً. طبقة `Application` تُجرّد الـ cache خلف واجهة (`ICacheService`) لإبقاء النواة نظيفة.

---

## 6) Phase 4 — Intelligence & Integrations (التمييز التنافسي)

**الهدف:** ميزات تميّزنا عن المنافسين (انظر مقارنة [01](01-Project-Overview.md) §7) وتزيد قيمة الاشتراك.

| الميزة | الوصف | الأولوية |
|--------|-------|----------|
| **AI Demand Forecasting** | التنبؤ بالطلب لكل منتج/فرع لأتمتة إعادة الطلب | 🟠 مهمّة |
| **WhatsApp Integration** | إرسال الفواتير/الإشعارات/تأكيد الطلب للعملاء | 🟠 مهمّة |
| **e-Invoicing حكومي** | فوترة إلكترونية معتمدة (قطرياً حسب السوق) | 🟠 مهمّة (حسب البلد) |
| تنبيهات ذكية | نفاد مخزون، بطء حركة، انتهاء صلاحية (FEFO للصيدليات/الألبان) | 🟡 لطيفة |
| توصيات تسعير/عروض | اقتراحات مبنية على البيانات التاريخية | 🟢 مستقبلية |
| تكامل بوّابات دفع | دفع إلكتروني عبر POS والفواتير | 🟠 مهمّة |
| تكامل محاسبي خارجي | تصدير لأنظمة GL خارجية (حتى نبني GL كامل — Phase خارج النطاق الحالي) | 🟡 لطيفة |

**تنبيه معماري:** ميزات AI تُبنى كخدمات منفصلة (Microservice/Background) تستهلك بيانات القراءة، ولا تُدخل اعتمادية ثقيلة داخل النواة المحاسبية.

---

## 7) Phase 5 — Platform & Ecosystem (منصّة كاملة)

**الهدف:** التحوّل من منتج إلى منصّة قابلة للتوسّع والامتداد بطرف ثالث.

| الميزة | الوصف | الأولوية |
|--------|-------|----------|
| **Sharding** | تقسيم أفقي حسب `TenantId` + Tenant Catalog للتوجيه (مصمّم مسبقاً — [03](03-Database-Strategy.md) §5) | 🟠 مهمّة |
| **Hybrid Tenancy** | ترقية المستأجرين الضخام (VIP) إلى DB مخصّصة | 🟡 لطيفة |
| **Domain-per-Tenant** | نطاق مخصّص لكل مستأجر (`store.tenant.com`) + شهادات آلية | 🟡 لطيفة |
| **Marketplace للإضافات** | نظام Plugins/Extensions لطرف ثالث فوق نقاط امتداد معرّفة | 🟢 رؤية |
| **Public API + Webhooks** | API عام موثّق + أحداث خارجة للمطوّرين | 🟠 مهمّة |
| **Billing & Subscriptions** | فوترة الاشتراكات، خطط، حدود استخدام لكل مستأجر | 🔴 حرجة (للاستدامة) |
| **Marketplace بيانات/تكاملات** | متجر تكاملات جاهزة (شحن، دفع، محاسبة) | 🟢 رؤية |

## 8) الديون التقنية المتوقّعة (Anticipated Technical Debt)

نُوثّق الديون **مسبقاً** لإدارتها بوعي لا لاكتشافها متأخّرين.

| الدَّين | متى يظهر | الأثر | خطة السداد |
|--------|----------|-------|-------------|
| **استعادة مستأجر واحد معقّدة** | Phase 2+ (نتيجة Shared-Schema) | صعوبة استعادة عميل بمفرده | أدوات تصدير/استيراد بالـ `TenantId` + Point-in-Time منطقي |
| **الجار الصاخب (Noisy Neighbor)** | Phase 3 (حمل متزايد) | مستأجر ثقيل يبطئ الآخرين | مراقبة موارد، حدود، ثم Sharding/Hybrid (Phase 5) |
| **غياب GL محاسبي كامل** | مبكّر (خارج النطاق — [01](01-Project-Overview.md)) | حاجة تصدير خارجي للمحاسبة العامّة | بناء GL تدريجياً بعد استقرار AR/AP |
| **CQRS جزئي** | Phase 2-3 | بعض المسارات CRUD بسيطة بلا فصل قراءة/كتابة | تطبيق CQRS عند الحاجة فقط (مبدأ [02](02-System-Architecture.md)) |
| **تخصيص schema موحّد للكل** | متأصّل في Shared-Schema | لا يمكن تخصيص أعمدة لمستأجر بمفرده | Custom Fields عبر JSON المسموح ([03](03-Database-Strategy.md) §8) |
| **إدخال Cache متأخّر** | Phase 3 | خطر عدم اتساق cache إن لم يُصمّم الإبطال جيداً | واجهة `ICacheService` + استراتيجية إبطال واضحة |
| **مزامنة POS Offline** | Phase 3 | تعارضات مزامنة، ترقيم فواتير محلي | تصميم قائم على `Sequences` + حلّ تعارض واضح |
| **ترحيلات EF على بيانات ضخمة** | Phase 3+ | ترحيلة واحدة تلمس ملايين الصفوف | ترحيلات على دفعات (batched) + نوافذ صيانة |
