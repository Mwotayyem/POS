# 01 — Project Overview (نظرة عامة على المشروع)

> **Smart ERP POS** — منصّة **SaaS** تجارية متعدّدة المستأجرين (Multi-Tenant) تجمع بين **نظام تخطيط موارد المؤسسة (ERP)** و**نقطة البيع (POS)** في مصدر كود واحد ونشر واحد، مبنية على **.NET 9** و **SQL Server 2022**.

---

## 1) المشكلة التي يحلّها النظام (Problem Statement)

الشركات الصغيرة والمتوسطة (SMEs) في قطاع التجزئة تواجه ثلاث مشكلات مزمنة:

1. **التجزئة (Fragmentation):** نظام POS منفصل عن المحاسبة، منفصل عن المخزون، منفصل عن المشتريات. البيانات لا تتزامن، والتقارير يدوية.
2. **التكلفة (Cost):** الأنظمة العالمية (SAP B1, Dynamics 365) باهظة (رخص + استشاريون + خوادم)، خارج متناول متجر بقالة أو صيدلية.
3. **عدم المرونة (Rigidity):** الأنظمة المحلية غالباً تُثبَّت على كل جهاز على حدة (On-Premise)، تتطلّب فنّياً لكل عميل، ولا تدعم التعدّد الحقيقي للمتاجر أو التخصيص دون تعديل الكود.

**Smart ERP POS** يحلّ ذلك بمنصّة سحابية واحدة:

- **مصدر كود واحد** يخدم آلاف العملاء (Tenants).
- **نشر واحد** — إضافة عميل جديد = صفّ في جدول `Tenants`، لا تعديل كود ولا نشر جديد.
- **تكامل كامل**: البيع يخفّض المخزون، الشراء يزيده، والمحاسبة تُحدَّث لحظياً — كلّه في معاملة قاعدة بيانات واحدة (ACID).
- **تخصيص كامل** (شعار، ألوان، عملة، ضريبة، لغة، قوالب طباعة) عبر الإعدادات لا الكود.

## 2) الأهداف (Goals & Objectives)

### أهداف العمل (Business Goals)

| # | الهدف | مؤشّر القياس |
|---|-------|--------------|
| G1 | خدمة آلاف المستأجرين من نشر واحد | عدد Tenants نشطة دون تعديل كود |
| G2 | خفض تكلفة الدخول للعميل | تفعيل مستأجر جديد < 10 دقائق، بلا فنّي |
| G3 | تغطية 10 قطاعات تجزئة بنفس النواة | Business Type قابل للإعداد |
| G4 | تكامل POS ↔ ERP لحظي | صفر تأخير بين البيع وتحديث المخزون |

### أهداف تقنية (Technical Goals)

| # | الهدف | المعيار |
|---|-------|---------|
| T1 | عزل تام للبيانات بين المستأجرين | Global Query Filter + RLS (defense-in-depth) |
| T2 | سلامة محاسبية | Soft Delete إجباري، Transactions ذرّية، `DECIMAL(18,4)` |
| T3 | قابلية التوسّع الأفقي مستقبلاً | تصميم يسمح بـ Sharding لاحقاً دون إعادة كتابة |
| T4 | زمن استجابة POS < 200ms للبيع | فهرسة على `TenantId`, RCSI, caching |
| T5 | قابلية الصيانة | Clean Architecture، فصل الطبقات، اختبارات |

## 3) النطاق (Scope)

### داخل النطاق (In-Scope)

| المجال | التغطية |
|--------|---------|
| **Tenancy & Stores** | مستأجرون، فروع/متاجر متعدّدة، إعدادات لكل مستوى |
| **Identity & Access** | تسجيل دخول، JWT + Refresh Token، أدوار وصلاحيات دقيقة (RBAC) |
| **Catalog** | منتجات، باركود متعدّد، وحدات قياس، متغيّرات، تصنيفات شجرية، علامات تجارية |
| **Partners** | موردون، عملاء، حدود ائتمان، نقاط ولاء، دفعات |
| **Inventory** | مستودعات، أرصدة، حركات مخزون، تسويات، تحويلات بين الفروع |
| **Purchasing** | أوامر شراء، فواتير شراء، استلام، مرتجعات شراء |
| **Sales** | فواتير بيع، مرتجعات بيع، دفعات، ضرائب متعدّدة |
| **POS** | كاشير، شفتات (Shifts)، صندوق نقدية، تعليق الفواتير، إغلاق يومي (EOD) |
| **Promotions** | عروض، قواعد عروض، خصومات، تتبّع استخدام العروض |
| **Reporting** | تقارير مبيعات/مشتريات/مخزون/أرباح، لوحة تحكّم لحظية |
| **Ops** | إشعارات لحظية (SignalR)، سجل تدقيق (Audit Log)، إعدادات |

### خارج النطاق (Out-of-Scope — للمرحلة الحالية)

| المجال | السبب | متى؟ |
|--------|-------|------|
| محاسبة عامة كاملة (GL, دفتر أستاذ، ميزانية) | تعقيد كبير، نبدأ بالمحاسبة الفرعية (AR/AP) | Phase 3+ |
| كشوف الرواتب (Payroll) | خارج نطاق التجزئة الأساسي | مستقبلاً |
| تصنيع (Manufacturing / BOM كامل) | قطاع مختلف | Phase 4+ |
| تطبيق جوّال أصلي (Native Mobile) | نبدأ بـ Web Responsive | Phase 3 |
| تكامل e-Invoicing حكومي لكل الدول | يُبنى قطرياً حسب الطلب | حسب السوق |
| Marketplace للإضافات (Plugins) | يتطلّب نضج المنصّة | Phase 5 |

> **مبدأ حاكم:** كل ما هو داخل النطاق **قابل للإعداد (Configurable)** — لا يُعدَّل الكود المصدري عند استقبال عميل جديد أو قطاع جديد.

## 4) القطاعات المستهدفة (Target Segments)

| القطاع | Business Type | خصوصيات يجب دعمها |
|--------|---------------|-------------------|
| السوبرماركت | `Supermarket` | باركود وزني، وحدات متعددة، عروض كثيفة |

| محلات الألبان | `Dairy Shop` | تواريخ صلاحية قصيرة، FEFO |
| المطاعم | `Restaurant` | طاولات، modifiers، مطبخ (لاحقاً) |

## 5) الجمهور المستهدف (Audience & Personas)

| الشخصية (Persona) | الدور | ما يهمّه |
|-------------------|-------|----------|
| **Tenant Owner** | مالك الشركة/سلسلة المتاجر | تقارير أرباح، تحكّم بالفروع، تكلفة اشتراك واضحة |
| **Store Manager** | مدير فرع | مخزون فرعه، أداء الكاشيرين، الطلبيات |
| **Cashier** | موظّف نقطة البيع | واجهة بيع سريعة، بلا تعقيد، تعمل offline-tolerant |
| **Accountant** | محاسب | دقّة الأرقام، مطابقة، تدقيق كامل |
| **Purchasing Officer** | مسؤول مشتريات | أوامر شراء، استلام، أرصدة موردين |
| **Platform Admin (نحن)** | مشغّل المنصّة | إدارة المستأجرين، المراقبة، النشر، الفوترة |

### جمهور هذا التوثيق

- **المطوّرون** الذين يبنون/يصونون النظام (ومساعد الـ AI الذي يولّد الكود وفق `AI-Prompt/`).
- **المعماريون** لمراجعة القرارات التصميمية.
- **مسؤولو الجودة** لفهم قواعد العمل واختبارها.

## 6) معايير النجاح (Success Criteria)

### معايير وظيفية

- ✅ فتح مستأجر جديد وتشغيل أول عملية بيع في أقل من **10 دقائق** دون تدخّل هندسي.
- ✅ عملية بيع POS كاملة (فاتورة + بنود + خصم مخزون + حركة صندوق) في **معاملة ذرّية واحدة**.
- ✅ صفر تسرّب بيانات بين المستأجرين (يُثبَت باختبارات عزل آلية).
- ✅ استعادة كاملة لأي فاتورة/حركة محذوفة (Soft Delete + Audit).

### معايير غير وظيفية (NFRs)

| المعيار | الهدف |
|---------|-------|
| زمن استجابة البيع (p95) | < 200ms |
| زمن استجابة التقارير (p95) | < 2s |
| التوفّر (Availability) | 99.9% |
| RPO (فقد البيانات المقبول) | ≤ 5 دقائق |
| RTO (زمن الاستعادة) | ≤ 30 دقيقة |
| السعة | آلاف المستأجرين على نشر واحد |

## 7) مقارنة موجزة بالمنافسين (Competitive Landscape)

| المعيار | **Smart ERP POS** | Dynamics 365 BC | SAP Business One | Odoo | Zoho Inventory |
|---------|-------------------|-----------------|------------------|------|----------------|
| **النموذج** | SaaS متعدّد المستأجرين حقيقي | SaaS/On-Prem | On-Prem/Cloud | SaaS/On-Prem/Open | SaaS |
| **POS متكامل أصلي** | ✅ جوهر المنتج | إضافة/طرف ثالث | إضافة | تطبيق POS منفصل | محدود |
| **تكلفة الدخول** | منخفضة جداً | عالية جداً | عالية جداً | متوسطة (open core) | منخفضة |
| **التعقيد للـ SME** | بسيط، مُعَدّ مسبقاً للقطاع | معقّد | معقّد جداً | متوسط-معقّد | بسيط |
| **التخصيص دون كود** | ✅ إعدادات + Feature Flags | يتطلّب شركاء | يتطلّب شركاء | يتطلّب مطوّر | محدود |
| **دعم عربي / RTL أصلي** | ✅ أساسي | جزئي | جزئي | جزئي | جزئي |
| **العزل** | Row-level + RLS اختياري | Tenant-level | حسب النشر | حسب النشر | Tenant-level |
| **الشمولية (ERP كامل)** | متدرّج (Roadmap) | ✅ شامل | ✅ شامل | ✅ شامل | مخزون فقط |

### موقعنا التنافسي (Positioning)

> **"قوة ERP بتكلفة وبساطة POS، مُصمّم أصلاً للسوق العربي ولقطاع التجزئة الصغير والمتوسط."**

- **ضد Dynamics/SAP:** نتفوّق في التكلفة، سرعة الإطلاق، وبساطة الاستخدام لـ SME.
- **ضد Odoo:** نتفوّق في تجربة SaaS الجاهزة (لا نصب/صيانة) ودعم عربي أصلي وPOS كنواة لا كإضافة.
- **ضد Zoho:** نتفوّق في الشمولية (ERP لا مجرّد مخزون) وعمق الـ POS والمحاسبة الفرعية.

نتنازل عن الشمولية الكاملة للـ ERP في البداية (out-of-scope أعلاه) مقابل **عمق وجودة في نطاق التجزئة** — ثم نتوسّع عبر [30-Future-Roadmap.md](30-Future-Roadmap.md).

## 8) المبادئ الحاكمة للمنتج (Product Principles)

1. **Configuration over Code** — كل اختلاف بين العملاء يُحلّ بالإعداد لا بفرع كود.
2. **Tenant Isolation First** — العزل قرار معماري لا ميزة لاحقة (انظر [03-Database-Strategy.md](03-Database-Strategy.md)).
3. **Accounting Integrity** — لا حذف فعلي، لا `FLOAT` للأموال، لا حركة خارج معاملة.
4. **Single Source of Truth** — قاعدة بيانات علائقية مطبّعة، لا JSON للبيانات المحاسبية (انظر [04-Database-Design.md](04-Database-Design.md)).
5. **Progressive Scale** — نبدأ Shared-Schema، ونصمّم بحيث يمكن الانتقال لـ Sharding دون إعادة كتابة.
