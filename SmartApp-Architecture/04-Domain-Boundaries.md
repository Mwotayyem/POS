# 04 — Domain Boundaries & Modules (حدود الوحدات والنطاقات)

> يحدّد هذا الملف **حدود الوحدات (Bounded Contexts / Modules)** في SmartApp، والفصل بين **النواة العامّة** و**امتدادات POS المستقبلية**، وكيف تُضاف الامتدادات **دون إعادة تصميم النواة**. هذا هو الملف الذي يضمن أن "POS امتداد لا أساس".

---

## 1) المبدأ الحاكم: Core ≠ POS

```
┌──────────────────────────────────────────────────────────────┐
│                     SmartApp Core (الآن)                     │
│  نظام إدارة أعمال عامّ — لا يعرف شيئاً عن POS                │
│                                                              │
│  Tenancy · Identity · Catalog · Inventory · Partners ·      │
│  Sales · Purchases · Reporting · Audit · Settings           │
└──────────────────────────┬───────────────────────────────────┘
                           │ يبني فوقها (يعتمد عليها)
                           ▼
┌──────────────────────────────────────────────────────────────┐
│               POS & Advanced Extensions (لاحقاً)              │
│  تبني فوق النواة عبر واجهاتها العامّة — لا تعدّل جداولها      │
│                                                              │
│  POS Terminal · Cashier Shifts · Barcode Terminal ·         │
│  Promotions/Offers · Loyalty · Advanced Multi-store         │
└──────────────────────────────────────────────────────────────┘
```

**قاعدتان صارمتان:**

1. **النواة لا تعتمد على الامتداد** — لا يوجد في كود النواة أي مرجع لـ POS. النواة تُبنى وتعمل كاملةً بدونه.
2. **الامتداد يعتمد على النواة عبر واجهاتها فقط** — POS يستدعي `ISalesService` / `IInventoryService` (واجهات النواة)، ولا يعدّل جداول النواة الأساسية.

## 2) وحدات النواة (Core Modules) — الحدود والمسؤوليات

### 2.1 Tenancy Management

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | تعريف المستأجرين (العملاء) وإدارة حالتهم اليدوية |
| **الكيانات** | `Tenant`, `TenantSetting` |
| **القيمة المحورية** | `TenantStatus` = `Active` / `Suspended` / `Disabled` — يتحكّم بها مالك النظام |
| **الحدود** | يملك مفهوم "من هو المستأجر"؛ كل الوحدات الأخرى تستهلك `TenantId` منه ولا تعرّفه |
| **من يديرها** | **مالك النظام فقط** (System Owner) — عبر endpoints خاصّة محميّة، ليست ضمن سياق مستأجر |

> **مهمّ:** إدارة المستأجرين (إنشاء/تفعيل/تعطيل) تجري خارج سياق العزل العادي — لأن مالك النظام فوق المستأجرين. تفصيل في [09-Multi-Tenant.md](09-Multi-Tenant.md) §"إدارة مالك النظام".

### 2.2 Identity & Access Control

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | المصادقة (Login/Refresh/Logout)، كلمات المرور، المستخدمون، الأدوار، الصلاحيات |
| **الكيانات** | `AppUser`, `AppRole`, `Permission`, `RolePermission`, `RefreshToken` |
| **الحدود** | يملك "من هو المستخدم وما صلاحياته"؛ كل الوحدات تستهلك الصلاحيات ولا تعرّفها |
| **RBAC** | صلاحيات بنمط `resource.action` (مثل `products.create`) — تفصيل في [10-Identity-RBAC.md](10-Identity-RBAC.md) |

### 2.3 Product Catalog

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | المنتجات، التصنيفات، الوحدات، الباركود |
| **الكيانات** | `Product`, `Category`, `Unit`, `ProductUnit`, `ProductBarcode` |
| **الحدود** | يملك "تعريف المنتج"؛ Inventory وSales/Purchases تشير للمنتج ولا تعرّفه |

### 2.4 Inventory Core

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | الأرصدة الحالية + سجل الحركات + تكلفة WAC + التسويات |
| **الكيانات** | `Stock`, `StockMovement` (**Append-Only**), `StockAdjustment` |
| **القاعدة المحورية** | كل تغيير في الرصيد = حركة في `StockMovements` (لا تُعدَّل، تُصحَّح بحركة معاكسة). التكلفة **Weighted Average Cost** |
| **الحدود** | يملك "كم لدينا وبأي تكلفة"؛ Sales/Purchases تُحدث الرصيد عبر واجهته لا مباشرة |

### 2.5 Partners (Customers & Suppliers)

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | العملاء والموردون وأرصدتهم ومدفوعاتهم |
| **الكيانات** | `Customer`, `Supplier`, `CustomerPayment`, `SupplierPayment` |
| **الحدود** | يملك "مع من نتعامل"؛ Sales تشير لعميل، Purchases تشير لمورد |

### 2.6 Sales Management

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | فواتير البيع وبنودها والمرتجعات |
| **الكيانات** | `SalesInvoice`, `SalesInvoiceItem`, `SalesReturn`, `SalesReturnItem` |
| **القواعد المحورية** | snapshot للسعر/الضريبة في البند · **المرتجع بسعر أصلي مجمّد** · منع الإرجاع الزائد |
| **الحدود** | ينشئ حركة مخزون **صادرة** (عبر Inventory) وحركة رصيد عميل (عبر Partners) ضمن معاملة واحدة |

### 2.7 Purchase Management

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | فواتير الشراء وبنودها والمرتجعات وأثرها على التكلفة |
| **الكيانات** | `PurchaseInvoice`, `PurchaseInvoiceItem`, `PurchaseReturn`, `PurchaseReturnItem` |
| **القواعد المحورية** | الشراء يُحدّث WAC · المرتجع يعكس أثر الرصيد على المورد |
| **الحدود** | ينشئ حركة مخزون **واردة** ويحدّث تكلفة WAC ورصيد المورد ضمن معاملة واحدة |

### 2.8 Reporting

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | تقارير القراءة فقط (Queries) عبر الوحدات |
| **الحدود** | **قراءة فقط** — لا يكتب بيانات. يقرأ من جداول الوحدات مع احترام العزل |

### 2.9 Audit Logging

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | تسجيل من غيّر ماذا ومتى على البيانات الحسّاسة |
| **الكيانات** | `AuditLog` (**Append-Only**) |
| **الحدود** | يُكتب تلقائياً عبر Interceptor/Behavior — لا يُعدَّل ولا يُحذَف أبداً |

### 2.10 System Settings

| البُعد | التفصيل |
|--------|----------|
| **المسؤولية** | إعدادات المستأجر (عملة، ضريبة، منطقة زمنية، ثيم، ترقيم مستندات) |
| **الكيانات** | `TenantSetting`, `Sequence` |
| **الحدود** | يوفّر التهيئة لبقية الوحدات (data-driven) — لا منطق أعمال |

## 3) خريطة اعتماد الوحدات (Module Dependency Map)

```
                          Tenancy  ◄──────── (كل الوحدات تستهلك TenantId)
                             ▲
                          Identity ◄──────── (كل الوحدات تستهلك Permissions)
                             ▲
        ┌────────────┬───────┴────────┬─────────────┐
        │            │                │             │
     Catalog     Partners         Settings       Audit
        ▲            ▲                              ▲
        │            │                              │
        └──────┬─────┘                              │
               ▼                                    │
           Inventory ◄──────────────────────────────┤
               ▲                                    │
        ┌──────┴──────┐                             │
        │             │                             │
      Sales      Purchases ────────────────────────►┘
        │             │
        └──────┬──────┘
               ▼
           Reporting  (قراءة فقط من الجميع)
```

**قواعد الاعتماد بين الوحدات:**

- `Sales` و`Purchases` يعتمدان على: `Catalog` (المنتج) + `Inventory` (الرصيد) + `Partners` (العميل/المورد).
- `Inventory` يعتمد على `Catalog` (لا معنى لرصيد بلا منتج).
- `Reporting` يقرأ من الجميع، ولا يُكتب إليه أحد.
- `Audit` يُكتب تلقائياً من الجميع عبر البنية التحتية.
- **لا اعتماد دائري** بين الوحدات.

## 4) التواصل بين الوحدات (Inter-Module Communication)

| الآلية | متى | مثال |
|--------|-----|------|
| **واجهة خدمة (Service Interface)** | استدعاء متزامن ضمن نفس المعاملة | `Sales` يستدعي `IInventoryService.RecordOutbound(...)` لخصم المخزون |
| **Domain Events** | تفاعل غير متزامن/جانبي | حدث `SalesInvoiceCreated` يُطلق تحديث نقاط الولاء (في الامتداد المستقبلي) |
| **قراءة عبر Query** | التقارير | `Reporting` يستعلم مباشرة (قراءة فقط) |

> **قاعدة:** وحدة لا تصل إلى **جداول** وحدة أخرى مباشرةً في عمليات الكتابة — تمرّ عبر واجهتها. هذا يحفظ الحدود ويسمح بتغيير التنفيذ الداخلي دون كسر المستهلكين.

## 5) كيف يُضاف POS كامتداد (Extension Pattern)

عند الوصول لمرحلة POS، يُضاف كوحدات جديدة **موازية** للنواة:

```
Domain/Pos/          PosShift, PosSession, CashDrawerMovement, SuspendedInvoice
Application/Pos/      OpenShiftCommand, CloseShiftCommand, ProcessPosSaleCommand, …
Persistence/Configurations/Pos/
API/Controllers/v1/PosController.cs
```

**كيف يبني POS فوق النواة دون تعديلها:**

| احتياج POS | كيف يُلبّى من النواة |
|-----------|---------------------|
| إنشاء بيع سريع | يستدعي `ISalesService.CreateInvoice(...)` — نفس منطق البيع الأساسي |
| خصم المخزون | عبر `IInventoryService` — نفس حركات `StockMovements` |
| رصيد العميل | عبر `Partners` |
| الترقيم | عبر `Sequences` (نوع مستند جديد `POS_SALE`) |
| العروض | امتداد `Promotions` يضيف طبقة خصم قبل الحفظ |

**ما يضيفه POS حصراً (لا يمسّ النواة):** دورة الشفت (Open/Close)، جرد الكاش، الجلسات، تعليق الفواتير، واجهة اللمس. هذه مفاهيم POS بحتة تعيش في وحدته.

> **اختبار السلامة:** لو حذفنا مجلدات `Pos/` بالكامل، يجب أن **يُبنى النظام ويعمل** كنواة كاملة. إن لم يحدث، فقد تسرّب POS إلى النواة = خرق للحدود.

## 6) نقاط التوسّع المصمَّمة مسبقاً (Designed Extension Points)

| نقطة التوسّع | كيف صُمّمت لتقبل الامتداد |
|--------------|---------------------------|
| **الفروع (Multi-store)** | `Tenant` هو الحدّ الآن؛ يُضاف `StoreId` لاحقاً **فقط** للكيانات التي تحتاج عمليات على مستوى فرع (Stock, Sales, Purchases) دون لمس بقية الجداول |
| **العروض (Promotions)** | نقطة حقن في مسار حساب الفاتورة (قبل الحفظ) لتطبيق خصومات |
| **الولاء (Loyalty)** | يستمع لـ `SalesInvoiceCreated` event |
| **الترقيم** | `Sequences` يقبل أنواع مستندات جديدة (`POS_SALE`) دون تغيير schema |
| **RLS** | الأعمدة والعزل جاهزان لتفعيل SQL RLS كطبقة تقوية |

## 7) خلاصة الحدود

| الوحدة | يملك | يعتمد على | يُقرأ منه فقط |
|--------|------|-----------|:-------------:|
| Tenancy | المستأجر وحالته | — | ✅ (الكل) |
| Identity | المستخدم والصلاحيات | Tenancy | ✅ (الكل) |
| Catalog | تعريف المنتج | Tenancy, Identity | — |
| Inventory | الرصيد والتكلفة | Catalog | — |
| Partners | العملاء/الموردون | Tenancy | — |
| Sales | فواتير البيع | Catalog, Inventory, Partners | — |
| Purchases | فواتير الشراء | Catalog, Inventory, Partners | — |
| Reporting | لا شيء (قراءة) | الكل | — |
| Audit | سجل التدقيق | — (يُكتب تلقائياً) | ✅ |
| Settings | التهيئة | Tenancy | ✅ |
| **POS (لاحقاً)** | الشفت/الجلسة | Sales, Inventory, Partners | — |
